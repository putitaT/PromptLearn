# สถาปัตยกรรม Flutter ของ PromptLearn

เอกสารนี้ใช้ตัดสินใจว่าจะสร้างไฟล์ที่ไหนเมื่อเพิ่มฟีเจอร์ให้แอปครูและนักเรียน เป้าหมายแรกคือแท็บเล็ต Android ทั้งแนวตั้ง แนวนอน และโหมดแบ่งหน้าจอ โดยใช้โค้ด Flutter ชุดเดียวกับ iPad ปัจจุบันแอปเริ่มที่ `lib/main.dart` ผังด้านล่างเป็นโครงสร้างเป้าหมาย ให้สร้างแต่ละโฟลเดอร์พร้อมไฟล์แรกที่ใช้งานจริง

## โครงสร้างใน frontend

จัดหน้าจอตามงานของผู้ใช้ และจัดข้อมูลตามสิ่งที่ฟีเจอร์ต่าง ๆ ใช้ร่วมกัน เช่น ครูแก้ syllabus และนักเรียนอ่าน syllabus ผ่าน repository เดียวกัน แต่มี ViewModel คนละตัวได้เมื่อคำสั่งและสถานะของหน้าจอต่างกัน

```text
frontend/
├── lib/
│   ├── main.dart                         # จุดเริ่มแอป
│   ├── app/
│   │   ├── prompt_learn_app.dart         # MaterialApp
│   │   ├── dependencies.dart             # สร้าง service และ repository แล้วส่งให้ผู้ใช้
│   │   └── routing/                      # ประกอบหน้าจอ ส่งต่อ ID และสร้าง ViewModel
│   ├── ui/
│   │   ├── core/
│   │   │   ├── theme/                    # สี ตัวอักษร และระยะห่างที่ใช้ร่วมกัน
│   │   │   ├── layout/                   # โครงหน้าจอที่ปรับตามพื้นที่
│   │   │   └── widgets/                  # widget ที่มีหลายฟีเจอร์ใช้งานจริง
│   │   └── features/
│   │       └── syllabus/
│   │           ├── views/syllabus_editor_view.dart
│   │           ├── view_models/syllabus_editor_view_model.dart
│   │           └── widgets/chapter_score_field.dart
│   ├── domain/
│   │   ├── models/course_syllabus.dart   # ข้อมูลรายวิชาที่แอปใช้
│   │   ├── repositories/syllabus_repository.dart
│   │   └── use_cases/                    # กฎที่ใช้หลายหน้าหรืองานข้าม repository
│   └── data/
│       ├── models/syllabus_dto.dart      # รูปแบบข้อมูลรับส่งกับ backend
│       ├── repositories/api_syllabus_repository.dart
│       └── services/syllabus_api_service.dart
├── test/                                 # ใช้เส้นทางตาม lib/ และลงท้ายด้วย _test.dart
├── integration_test/                     # ทดสอบเส้นทางผู้ใช้ข้ามหน้าจอ
├── android/                              # การตั้งค่าและโค้ดเฉพาะ Android
└── ios/                                  # การตั้งค่าและโค้ดเฉพาะ iOS
```

ตั้งชื่อไฟล์และโฟลเดอร์ Dart ด้วย `lower_snake_case` ตั้งชื่อคลาสตามหน้าที่ เช่น `SyllabusEditorViewModel` เก็บ widget ที่รู้จักบทเรียน คะแนน หรือพฤติกรรมเฉพาะของหน้าไว้กับฟีเจอร์นั้น เมื่อมีหลายฟีเจอร์ใช้ส่วนแสดงผลเดียวกันจึงย้ายไป `ui/core/`

## หน้าที่ของแต่ละชั้น

| เมื่อต้องการทำอะไร | วางไว้ที่ไหน | ตัวอย่าง |
| --- | --- | --- |
| แสดงผล รับการแตะ และจัดพื้นที่ | View ใน `ui/features/<feature>/views/` | ครูกดบันทึกแล้ว View เรียก `viewModel.save()` |
| จัดการร่างบนหน้าจอและผลของคำสั่ง | ViewModel ในฟีเจอร์เดียวกัน | เก็บบทที่เลือก แสดงข้อผิดพลาด และป้องกันการกดบันทึกซ้ำระหว่างส่ง |
| นิยามความหมายหรือกฎของข้อมูล | `domain/models/` | `CourseSyllabus` เก็บแหล่งอ้างอิง บทเรียน จำนวนคาบ และสัดส่วนคะแนน |
| กำหนดว่าส่วนอื่นอ่านหรือเขียนข้อมูลอย่างไร | สัญญาใน `domain/repositories/` และตัวทำงานจริงใน `data/repositories/` | `SyllabusRepository` เปิดคำสั่งโหลดและบันทึก ตัวทำงานจริงแปลง DTO เป็นโมเดลรายวิชา |
| ติดต่อระบบภายนอก | `data/services/` | เรียก API อัปโหลดไฟล์ หรือเรียกปลั๊กอินบันทึกหน้าจอ |
| ประสานหลายแหล่งข้อมูลในงานเดียว | `domain/use_cases/` เมื่อจำเป็น | สร้างร่างแผนรายคาบจาก syllabus ฉบับที่เลือก แล้วเก็บร่างผ่าน repository ของ lesson plan |

เริ่มด้วย MVVM โดยให้ ViewModel ใช้ `ChangeNotifier` และเปิดสถานะให้อ่านแบบ immutable ส่วน View ใช้ `ListenableBuilder` ติดตามการเปลี่ยนแปลง ส่ง repository เข้า ViewModel ผ่าน constructor เพื่อให้ชุดทดสอบใช้ตัวจำลองได้ ให้ผู้สร้าง ViewModel ประจำหน้ารับผิดชอบ `dispose()` เมื่อปิดหน้า

ทิศทางการเรียกเมื่อครูบันทึกเป็น **View → ViewModel → SyllabusRepository → API service** โดย `app/` เป็นจุดที่เลือกตัวทำงานจริงของ repository ชั้น domain ใช้ Dart และไม่มี dependency ไปยัง widget, JSON หรือปลั๊กอิน เมื่อบันทึกสำเร็จ repository ส่งโมเดลกลับให้ ViewModel อัปเดตหน้า เมื่อบันทึกล้มเหลว ViewModel เก็บร่างเดิมและให้ครูลองใหม่ได้ แนวทางแบ่งความรับผิดชอบนี้อิง [คู่มือสถาปัตยกรรมของ Flutter](https://docs.flutter.dev/app-architecture/guide)

## ขอบเขตฟีเจอร์ตาม Teaching and Learning Cycle

ชื่อในคอลัมน์แรกคือโฟลเดอร์ภายใต้ `lib/ui/features/` ส่วนข้อมูลที่หลายหน้าต้องใช้ให้อ้างผ่าน repository ของเจ้าของข้อมูล

| ฟีเจอร์ | รับผิดชอบ | จุดเชื่อมกับงานอื่น |
| --- | --- | --- |
| `syllabus/` | ครูออกแบบและเผยแพร่โครงรายวิชา แหล่งอ้างอิง ตัวชี้วัดปลายทาง บท จำนวนคาบ และน้ำหนักคะแนน นักเรียนอ่านฉบับเผยแพร่ | แผนรายคาบอ้างถึงรายวิชาและบท |
| `lesson_planning/` | ครูเลือกวิธีสอน เช่น IBL จัดกิจกรรมตามเวลา และกำหนดแบบฝึกหัดหรือการบ้านท้ายคาบ | แผนบอกว่าจะสอนอะไร ส่วนคาบที่เกิดขึ้นจริงอ้างถึงแผนนั้น |
| `schedule/` | ครูและนักเรียนดูวันเรียน หัวข้อคาบถัดไป และวัน quiz | ประกอบข้อมูลคาบและการวัดผลผ่าน ID เมื่อเปิดรายการ |
| `materials/` | นำเข้า สร้าง หรือแก้สไลด์และสื่อเขียนด้วยปากกา รวมถึงสื่อที่ AI ช่วยร่าง | แนบสื่อเดียวกันกับแผนและเปิดสอนในคาบได้ |
| `classroom/` | เริ่มและจบคาบ เช็กชื่อตามตำแหน่ง และควบคุมการบันทึกหน้าจอ | ส่ง ID ของคาบให้ระบบบันทึกและติดตามสถานะอัปโหลด |
| `lesson_review/` | ดูคลิปย้อนหลัง transcript และถาม AI ณ เวลาที่เลือก | ทุกคำถามอ้างถึงคลิปและตำแหน่งเวลา งานถอดเสียงหรือตัดต่อทำที่ backend |
| `assessment/` | สร้างโจทย์จากภาพหรือฟอร์ม ออกแบบ rubric ส่งวิธีทำ ให้คำใบ้ และประเมินแบบ formative หรือ summative | เก็บผลรายข้อและข้อผิดพลาดตามงานและผู้เรียน |
| `insights/` | นักเรียนทบทวนจุดที่พลาด ครูดูผลรายบท การมีส่วนร่วม และข้อเสนอแนะหลังสอน | อ่านผลประเมินและข้อมูลจากคาบตามสิทธิ์ของผู้ใช้ |

ให้ครูและนักเรียนใช้รายวิชาและคาบชุดเดียวกัน แยกหน้าหรือคำสั่งตามบทบาทเมื่อพฤติกรรมต่างกัน เช่น ครูเห็นร่าง syllabus ส่วนนักเรียนเห็นฉบับเผยแพร่ ให้ backend ตรวจสิทธิ์อ่านและเขียนของรายวิชาอีกชั้นหนึ่ง

## หน้าจอสำหรับครูและนักเรียน

โครงนำทางเลือกหน้า Home จาก `UserRole` ที่อ่านจากการล็อกอิน โดยประกอบ `TeacherHomeView` หรือ `StudentHomeView` ใน `lib/ui/features/home/views/` ทั้งสองหน้าใช้ `HomeHeader` ขนาดขั้นต่ำ 100 dp ร่วมกันจาก `home/widgets/` และกลับเข้า Home ตามบทบาทใหม่เมื่อผู้ใช้สลับการล็อกอิน

ใช้รูปแบบเดียวกันกับฟีเจอร์ที่ครูและนักเรียนมีขั้นตอนต่างกัน โดยเก็บ View ของแต่ละบทบาทใน `views/` ของฟีเจอร์นั้น และเก็บส่วนประกอบที่ใช้ร่วมกันใน `widgets/` เพิ่ม ViewModel แยกเมื่อสถานะหรือคำสั่งของทั้งสองบทบาทต่างกัน ตัวอย่างใน syllabus คือหน้าจัดการฉบับร่างของครูและหน้าอ่านฉบับเผยแพร่ของนักเรียน

Teacher Home จัดคาบถัดไป แผนย่อ และตาราง Today ตามความกว้างที่เหลือหลังหัก Navbar และระยะขอบ หากพื้นที่แคบ การ์ดจะเรียงลงด้านล่าง ส่วนหน้าต่างแนวนอนที่เตี้ยใช้ความสูงของเนื้อหาจริงสำหรับแผนย่อเพื่อลดระยะเลื่อน

### หน้าสร้างข้อสอบของครู

ปุ่ม **Lesson Plan** บน Teacher Home เปิด `TeacherAssessmentBuilderView` ใน `ui/features/assessment/views/` ครูเลือก Quiz หรือ Homework แล้วเพิ่มคำถามแบบ Short answer, Show work, Multiple choice หรือ True or false ได้ ข้อมูลร่างเก็บชนิดโจทย์ ข้อความ คะแนน และตัวเลือก ผู้สอนตรวจหน้าตัวอย่างนักเรียนได้ก่อนเพิ่มเฉลยในขั้นถัดไป

หน้า Create Assessment ใช้ `AppPageLayout` ตรึง Header และเลื่อนเฉพาะเนื้อหา บนแท็บเล็ตวาง Settings กับ Questions ข้างกันและจัดปุ่ม Header ในแถวเดียว หน้าต่างแคบเรียง Questions ก่อน Settings เพื่อให้เข้าถึงปุ่มเขียนโจทย์ได้ทันที

`AssessmentDraftController` จัดลำดับการบันทึกร่างผ่าน `AssessmentDraftRepository` โดยใช้ SharedPreferences สำหรับร่างของ Unit 3 ในเครื่อง การนำเข้าโจทย์จากภาพและสร้างโจทย์ด้วย AI รอต่อในขั้นถัดไป

จากหน้า Create Assessment ปุ่ม Next เปิดหน้า Scoring rubric พร้อม Header แบบคงที่ บนแท็บเล็ตจัดรายการคำถาม เฉลย และ Design with AI เป็นสามคอลัมน์ ส่วนจอแคบจัดเรียงลงด้านล่าง `AssessmentRubricController` ขอร่างของแต่ละข้อพร้อมชื่อและกิจกรรมจาก Lesson Plan โดยใช้แผนตัวอย่าง 3.2 ที่แสดงบน Teacher Home ผ่าน `AssessmentRubricGenerator` และบันทึกเฉลยกับข้อเดิม เมื่อแก้โจทย์ ตัวเลือก หรือคะแนน ระบบจะขอร่างใหม่เมื่อกลับเข้าหน้าทำเฉลย

ครูแก้เฉลย เลือกคำตอบสำหรับ Multiple choice และ True / false และแก้คะแนน Show work ในตาราง คะแนน Full ต้องรวมเท่าคะแนนของข้อก่อนกดยืนยัน ข้อที่ AI มองว่านอกบทแสดงสีเหลืองพร้อมตัวเลือกเก็บหรือลบ ส่วนข้อผิดพลาดตัวอย่างแสดงสีแดง ครูแก้ร่างเองได้เมื่อ API ไม่พร้อมและตรวจข้อเสนอจาก Design with AI ก่อนนำไปใช้ การเผยแพร่ข้อสอบรอการเชื่อมระบบรายห้อง

### หน้าตั้งค่าก่อนสอนของครู

ปุ่ม **Start Class** จาก Teacher Home เปิด `TeacherClassSetupView` ใน `lib/ui/features/classroom/views/` ภายใน shell เดิม คงตำแหน่งการเลื่อนของ Home ไว้เมื่อกดย้อนกลับ Header ตรึงด้านบนด้วย `AppPageLayout` ส่วนข้อมูลคาบและแผนตัวอย่างใน `classroom/models/` ใช้ร่วมกับแผนแบบย่อบน Teacher Home

**Start teaching & recording** เปิดคำขอสิทธิ์ไมค์และการแชร์หน้าจอของ Android เมื่อเริ่มบันทึกจริง `TeacherTeachingView` แสดง REC และเวลาที่ผ่านไป แหล่ง **Whole screen** ใช้บันทึกต่อขณะสลับแอป หากต้องการแชร์เฉพาะ PromptLearn ให้เลือกรายการแอปในหน้าต่าง Android เมื่อระบบรองรับ การบันทึกใช้เสียงจากไมค์ของอุปกรณ์ [Android MediaProjection](https://developer.android.com/media/grow/media-projection)

`AndroidClassRecordingService` ใน `lib/data/services/` เชื่อม Flutter กับ `ClassRecordingService.kt` ผ่าน MethodChannel และ EventChannel ตัว foreground service ถือ MediaProjection และ MediaRecorder จึงทำงานต่อได้ระหว่างสลับแอป ปุ่ม **Stop & end class** ปิด session และปิดไฟล์ `.partial` เป็น MP4 แบบ H.264/AAC เมื่ออ่านพบทั้งแทร็กภาพและเสียง คลิปอยู่ในพื้นที่ส่วนตัว `noBackupFilesDir/class-recordings/` และ `ClassRecordingService.savedClips()` ส่งคืนพาธ ชื่อ และขนาดไฟล์สำหรับงานอัปโหลด

เมื่อบันทึก MP4 สำเร็จ แอปเปิด `TeacherClassEndedView` ภายใน shell เดิมและส่งพาธจาก `RecordingClip` ให้ `LocalClassClipPlayer` เล่นไฟล์โดยตรง เวลาใน Header และแถบเลื่อนอ่านจากไฟล์ หน้าตั้งค่าก่อนสอนมีปุ่ม **Last recording** เมื่อพบไฟล์ที่บันทึกไว้ [Flutter video_player](https://pub.dev/packages/video_player)

สไลด์ 14 หน้า โน้ตประจำสไลด์ เช็กชื่อ และคำถามนักเรียนใช้ข้อมูลตัวอย่าง หน้าจบคาบแสดงสถานะรออัปโหลด ถอดเสียง และสร้าง timestamp ปุ่มเผยแพร่รอเชื่อม backend

## Header และการเลื่อนหน้าจอ

หน้าที่มี Header ด้านบนใช้ [AppPageLayout](lib/ui/core/layout/app_page_layout.dart) ส่งชื่อหน้า ปุ่มย้อนกลับ และปุ่มแจ้งเตือนผ่านพารามิเตอร์ `header` เพื่อให้ตำแหน่งอยู่ด้านบนขณะเลื่อน ส่งเฉพาะเนื้อหาที่ต้องเลื่อนผ่าน `body` โดย `AppPageLayout` จัดพื้นที่และการเลื่อนให้

หน้าปัจจุบันที่ใช้โครงนี้ ได้แก่ Home ของครูและนักเรียน การบ้าน และหน้าเมนูหลักอื่น ๆ เมื่อเพิ่มหน้าใหม่ ให้วางรายการและกระดาษทดใน `body` โดยให้โครงนำทางแสดงหน้าในพื้นที่ที่มีความสูงจำกัด

## หน้าจอแท็บเล็ตและงานเฉพาะแพลตฟอร์ม

- หน้า syllabus ใช้ `LayoutBuilder` ดูความกว้างที่หน้ารับได้ เมื่อมีพื้นที่พอให้แสดงสารบัญบทด้านซ้ายและรายละเอียดด้านขวา เมื่อหน้าต่างแคบให้เปิดรายละเอียดทีละบท ทั้งสองรูปแบบใช้ ViewModel เดียวกัน จึงรักษาบทที่เลือกและข้อความที่กำลังแก้เมื่อหมุนเครื่องหรือแบ่งหน้าจอ [แนวทาง adaptive design ของ Flutter](https://docs.flutter.dev/ui/adaptive-responsive/best-practices)
- การแชร์หน้าจอ เช็กตำแหน่ง และเลือกไฟล์ให้เรียกผ่าน service ที่ห่อปลั๊กอิน วางโค้ด native ที่จำเป็นไว้ใน `android/` หรือ `ios/` ส่วน ViewModel รับผลที่นำไปแสดงได้ เช่น ผู้ใช้ปฏิเสธสิทธิ์ หรือการบันทึกหยุดลง
- งาน AI ที่ทำต่อหลังปิดหน้า เช่น สร้างแผนหรือถอดเสียง ให้ backend ส่ง ID ของงานกลับมา แอปใช้ ID นั้นอ่านสถานะและเปิดผลลัพธ์อีกครั้งเมื่อครูกลับเข้าคาบ

## เริ่มพัฒนาจาก syllabus หนึ่งรายวิชา

1. นิยาม `CourseSyllabus` และสัญญา `SyllabusRepository` จากสิ่งที่ครูต้องกรอกและนักเรียนต้องอ่าน ใช้ repository แบบ in-memory ระหว่างที่ API ยังอยู่ระหว่างออกแบบ โดยข้อมูลตัวอย่างจะอยู่ถึงเวลาปิดแอป
2. ทำหน้าครูให้แก้บท จำนวนคาบ และน้ำหนักคะแนนได้ แล้วทำหน้าที่นักเรียนอ่านฉบับเผยแพร่ ให้ทั้งสองหน้ารับ repository instance เดียวกันจาก `app/`
3. เมื่อตกลง API contract แล้ว เพิ่ม DTO, API service และ repository ตัวที่เชื่อม backend เปลี่ยนตัวที่ส่งเข้าหน้าจอใน `app/dependencies.dart` จากนั้นต่อฟีเจอร์แผนรายคาบโดยอ้างถึงบทใน syllabus
4. ทดสอบ ViewModel เมื่อบันทึกสำเร็จและล้มเหลวใน `test/ui/features/syllabus/view_models/` ทดสอบการแปลงข้อมูลใน `test/data/repositories/` และทำ widget test สำหรับการหมุนหรือย่อหน้าต่างขณะมีร่างค้างอยู่ ก่อนส่งฟีเจอร์ให้ตรวจเส้นทางครูเผยแพร่ → นักเรียนเปิดอ่านบนแท็บเล็ต Android
